# 抢票系统：现状调研 + 架构设计

> 调研对象：大麦（cn.damai，淘系 mtop）、猫眼（com.sankuai.movie，美团系）、票星球、纷玩岛
> 主线：用户在手机上「模拟真人操作 App」抢票，而非协议层直连
> 日期：2026-02（资料截至本次检索）

---

## 产品定位（先定这个，再谈技术）

### 一句话

**不是"一个抢票脚本"，是"一套手机端自动化作业系统"，抢票是它的第一个场景插件。脚本是这套系统里最不值钱、最快过期的耗材。**

### 为什么"脚本"是死定位

| 问题 | 现实 |
|---|---|
| 无壁垒 | 买票流程 300 行；控件文本一变，任何人 20 分钟改完。你今天的优势，明天是公开代码 |
| 无复购 | 一次性交付，抢完就结束；用户下次要么自己改，要么找你改 |
| 单点上限 | 一台手机一个号 = 一张票。这个价值用户自己点也能拿到，凭什么付钱 |
| 法律定性已完成 | 北京东城区法院：**售卖刷票软件构成不正当竞争**（全国首例）。"卖软件"这条路在判例层面已经封了 |
| 供给过剩 | 抢票圈 QQ 群 2000 人、99 元入群、1099 元/半小时咨询——**卖铲子的人比买铲子的人多** |

### 三个可选定位

| 定位 | 交付物 | 谁付钱 | 壁垒 | 死法 |
|---|---|---|---|---|
| **① 卖脚本/卡密** | 一个 App / 一份 JS | 个人抢票者 | 无 | 判例已定性；用户不会用→退款；平台一封杀全废 |
| **② 代抢服务** | 帮你抢到，收服务费 | 抢不到票的人 | 设备+账号规模、响应速度 | 实名账号成本、规模法律风险、口碑崩塌一次就死 |
| **③ 自动化作业平台** | 设备农场 + 状态机引擎 + 时序引擎 + 观测台 | 有"手机端重复操作"需求的人（含自己团队） | **引擎 + 设备资产 + 场景库** | 做成通用 RPA 就会被大厂 RPA 正面打 |

**推荐 ③，但必须先想清一件事：它靠"稀缺资源"赚钱，不靠"代码"赚钱。**

真正稀缺的三样东西，代码一样都不占：

1. **通过设备可信检测的真机**（大麦 2025-04 起查设备/系统/应用完整性，模拟器与改机直接被拦）
2. **能过风控的实名账号**（一机一号一出口，账号是消耗品）
3. **毫秒级对齐开售的调度能力**（NTP + T-55ms 补偿 + 多机抢占，这是纯粹的执行力）

代码只是把这三样"用起来"的胶水。所以产品定义应该是：**把「设备 + 账号 + 时序」这三样稀缺资源调度到最优的工具**，而不是"一个能点得比人快的脚本"。

### 定位如何反向决定架构（差异明显，现在就得分叉）

| 维度 | ① 自用脚本 | ③ 作业平台 |
|---|---|---|
| 设备管理 | 手写一个 device_id | 设备池：注册/健康检查/占用锁/故障摘除 |
| 任务 | 硬编码一场演出 | 任务模型：演出/场次/票档优先级/观演人/开售时刻，可下发可撤销 |
| 时序 | 本机 sleep | 中心校时 + 每机独立倒计时 + T-55ms 参数化标定 |
| 观测 | print 日志 | 逐态截图 + 录屏 + 失败归因 + 成功率看板 |
| 多租户 | 不需要 | 需要（否则只能自己用，永远长不大） |
| 场景扩展 | 只做大麦 | 插件化（猫眼/票星球/纷玩岛/其他手机端重复操作） |

**分叉点只有一句话：这套东西只服务你自己（含朋友），还是要服务不认识的人？**
- 只服务自己 → 砍掉多租户/计费/设备池，1 台机 + 状态机 + 时序，两周能跑；
- 要服务别人 → 卖"平台"或卖"代抢结果"，**不卖"大麦抢票专用软件"**（那是判例靶心），先做 P2 多机编排再谈商业化。

## 0. 结论先行

1. **市面上真正的三条技术路线**，不是两条：① 协议层 RPC 发包（最快，13ms 级）② 设备内无障碍控件自动化（500ms 级）③ 主机侧 ADB 坐标/状态机（200ms~1s 级）。用户想做的"模拟人"实际是 ②③ 的混合体。
2. **②③ 在大麦上并没有被协议层淘汰**，因为 2025-04 之后大麦的主防线已经从"智能验证码"换成**金融级设备可信检测**（与 OPPO 合作的芯片级机密计算空间），它检查的是**设备完整性/系统完整性/应用完整性/恶意应用风险**——真机 + 官方正版 App + 不开 root/frida 的设备天然通过，反而是协议层方案（改机、模拟器、注入）被精准针对。所以"用真手机模拟真人"是当前**风控通过率最高**的路线，代价是延迟高一个数量级。
3. **决定成败的不是脚本，是四件工程事**：时序精度（毫秒级对准开售）、感知延迟（能不能在 200ms 内确认"票档可选/已锁单"）、设备与账号的一对一隔离、失败可回滚可观测。脚本本身 300 行就够。

## 1. 现状：三条路线各自的真实实现

### 1.1 路线 A：协议层直连（发包）

**代表实现**：[damaiqiangpiao/damai](https://github.com/damaiqiangpiao/damai) 社区、[博客园 APK 抢票接口加密参数分析](https://www.cnblogs.com/damaidamai/articles/18103810)

接口链（大麦，淘系 mtop）：

| 步骤 | 接口 | 关键入参 |
|---|---|---|
| 取详情 | `mtop.alibaba.damai.detail.getdetail` | `itemId` → 场次 / SKU / 价格 / 状态 |
| 构建订单 | `mtop.trade.order.build.h5` | `buyParam = itemId_count_skuId`（如 `716435462268_2_5005943905715`）+ `buyNow=true` + `exParams` |
| 提交订单 | `mtop.trade.order.create.h5` | `data = {"feature":"{\"gzip\":\"true\"}","params":"<base64(gzip(form_json))>"}` |

防线在 header 签名，不在 body：

```
x-sign / x-sgext / x-mini-wua / x-umt     ← mtopsdk.security.InnerSignImpl 生成
```

- `x-mini-wua` 内含**设备信息**，与设备绑定 → 算法复现出来也没用，必须"借"真设备的签名能力。
- 主流做法是 **Frida RPC**：在真机/模拟器上加载 frida-server，`frida-trace -U -j "InnerSignImpl!*"` 定位签名函数，然后 `rpc.exports` 把 `getSign(data)` 暴露给 PC 端 Python 调用。等于把手机当成一台"签名机"。
- 抓包链：`tcpdump + SSL_CTX_set_keylog_callback hook + Wireshark (Pre)-Master-Secret`（Android 9+ 用户证书不被信任，必须走 keylog 解密）。
- 性能上限：同城 TCP+TLS 预热后单请求 **~13ms**（票星球同构实现的实测值），一个开售时刻能打出 burst 并发。

**代价/风险**：改机/模拟器/frida 都是设备可信检测的靶点；`InnerSignImpl` 随版本变动；一旦被判定机刷，是**整批设备+账号**的连带封禁。

### 1.2 路线 B：设备内无障碍自动化（真·模拟人）

**代表实现**：[基于 AutoX.js 的抢票](https://brszzz.github.io/2025/01/01/52pojie-1792775-%E5%9F%BA%E4%BA%8E%E8%87%AA%E5%8A%A8%E5%8C%96%E5%B7%A5%E5%85%B7autoxjs%E7%9A%84%E6%8A%A2%E7%A5%A8/)（52pojie 作者，大麦 8.5.4）、[Mox-lab/Get-Ticket](https://github.com/Mox-lab/Get-Ticket)

形态：AutoX.js / 振飞脚本常驻手机，用**控件树**定位而不是坐标：

```javascript
// 等"票档"出现 = 已进入选座页
while (!id("tv_price_name").className("android.widget.TextView").textContains("票档").exists()) {
    click("立即");
}
// 缺票判断：同级 child(1).child(0).text() == "无票"
// 选场次 → 遍历票档跳过"缺货登记" → 点"1张"的 + 号加数量 → 勾观演人 → 提交订单
```

作者的实测结论（关键）：

- 订单详情页 → 提交订单页（含多张票 + 多观演人勾选）**≈ 0.5 秒**；
- 比人手快，但比发包慢；
- **滑块验证码**：AutoX.js 有 OpenCV 可算缺口位置，但**无障碍方式经常驱动不了滑块**，需要自行调系统 API 注入触摸事件；
- 优势：跨 App / 跨机型适配成本低（控件文本变了改一行）。

### 1.3 路线 C：主机侧 ADB 驱动（工程化最好）

**代表实现**：[TsungShr/ticket-sniper](https://github.com/TsungShr/ticket-sniper)（票星球 + 猫眼 + 大麦 + 淘宝四端）

它的量化数据是整个调研里最有参考价值的：

| 优化点 | 数据 |
|---|---|
| ADB tap（每次 fork adb 进程） | **~41ms** |
| ADB tap（**持久 shell 复用**） | **~16ms** |
| 猫眼「盲点模式」全流程（30 次连点 → 3 轮盲点序列 → 10 次提交） | **~200ms**（零 UI dump） |
| 猫眼「扫描模式」 | 每轮 uiautomator dump + XML 解析，兜底用 |
| 票星球 HTTP burst（连接池预热） | **~13ms/请求** |
| 时序 | NTP 阿里/腾讯/cn.ntp.org.cn 多服务器**多采样取中位数**，粗等到 T-200ms 后 1ms 忙等，**T-55ms 发射** |
| 协调 | `FIRST_COMPLETED`：任一平台成功即 `_stop_event` 停掉其余 |

三种执行范式在同一项目里的分工：
- **大麦**：纯坐标点击（`buy_btn: [1600, 2650]`、`confirm_btn: [920, 2500]`），因为大麦是自定义渲染，控件树不稳；
- **猫眼**：坐标 + UI dump 二选一（盲点 / 扫描）；
- **淘宝**：持久 shell + 像素检测确认 + 30 次 burst、gap 8ms、max 12s。

| 平台 | 现状 | 对方案的直接约束 |
|---|---|---|
| **大麦** | 2025-04 起与 OPPO 合作接入**金融级设备可信检测**（ColorOS 机密计算空间 / 芯片级安全虚拟化）：检测**设备完整性、系统完整性、应用完整性、恶意应用风险**，用来**替代智能验证码**；2024 全年拦截机刷下单 **30 亿次** | 改机/模拟器/root/frida/重打包 = 高风险命中；**真机裸环境才安全** |
| 大麦（mtop 层） | `x-mini-wua` 绑定设备，签名算法版本随 App 更新 | 协议方案必须持续维护 RPC 壳 |

| **猫眼** | 美团系风控（mtguard + 设备指纹 + 行为轨迹） | 高频等间隔点击是显著特征，必须加抖动 |
| **腾讯天御（文旅/票务客户通用方案）** | 三层：流量清洗 → **设备指纹（AI 混合专家模型识虚拟设备/群控）** → **RCE 风险打分动态调门槛** | 「动态调门槛」意味着同一策略不能长期不变，要做**成功率反馈闭环** |
| 实测现象 | 大麦会弹「哎哟喂，被挤爆啦」（限流/排队）、提交订单「当前人数过多」、部分演出加答题 | 必须做**重试 + 降级提示**，并把限流当作常态而非异常 |

## 3. 推荐架构（模拟人主线）

```
┌──────────────────────────────────────────────────────────────┐
│ L5 观测/回流  录屏+日志+截图 · 失败原因归类 · 成功率看板 · 策略AB │
├──────────────────────────────────────────────────────────────┤
│ L4 风控对抗   拟人节奏 · 单账号单设备 · 出口隔离 · 环境自检       │
├──────────────────────────────────────────────────────────────┤
│ L0 调度时序   NTP 校时 · T-55ms 发射 · 多任务/多设备编排 · 抢到即止│
├──────────────────────────────────────────────────────────────┤
│ L3 感知(状态机) 页面识别 → 可用性判定 → 动作决策（非盲点）        │
├──────────────────────────────────────────────────────────────┤
│ L2 执行      设备内无障碍 performAction（首选）/ ADB tap（兜底）  │
├──────────────────────────────────────────────────────────────┤
│ L1 设备     真机农场（首选）· 云手机（备选）· 模拟器（仅调试）    │
└──────────────────────────────────────────────────────────────┘
```

### 3.1 关键选型判断

**为什么不是「纯盲点坐标」（ticket-sniper 猫眼模式）？**
盲点 200ms 是真的快，但它是**赌**：赌弹窗没有、赌进场页没变、赌票档位置没动。真实抢票里有三个不确定源——排队弹窗、缺货登记、观演人弹窗——任一中招全流程空转。所以正确形态是 **盲点快通道 + 状态机校验**：

- `T-0` 起用盲点连点抢「立即购买」入口（不需要知道票档状态，点到就进）；
- 进入选座页后，**切到感知模式**：一次节点读取（设备内，不走 ADB dump）拿全部可选票档 + 缺货标记 + 观演人，然后连续动作；
- 提交后每秒一次极轻量校验（读「订单确认」页特征控件），失败立刻重打。

**为什么感知必须放设备内？**
`adb shell uiautomator dump /sdcard/x.xml && cat` 的往返是**几百毫秒级**（一次完整 dump 300~800ms，随页面复杂度变化，需自测），而 AutoX.js 通过 AccessibilityService 在进程内读节点树是**单帧级**。这是 ② 相对 ③ 的唯一决定性优势——**不是点击快，是感知快**。

**执行层用哪种点击？**

| 方式 | 延迟 | 抗检测 | 适用 |
|---|---|---|---|
| 无障碍 `node.performAction(ACTION_CLICK)` | 最快（View 级，等价 performClick） | 能被检测「无障碍服务已开启」 | 首选 |
| ADB `input tap x y`（持久 shell） | ~16ms | 不改无障碍，几乎无特征 | 兜底 / 无障碍被检测时 |
| ADB `input tap`（每次 fork） | ~41ms | 同上 | 不要用 |
| root `sendevent` 原始事件 | 最快、最像真人 | 需 root（大麦设备可信检测命中） | 不推荐 |

> **折中方案**：抢票窗口开始前才打开无障碍服务（平时关闭），窗口内用无障碍，窗口结束立刻关。降低"长期开启无障碍"这一静态特征的暴露面。
>
> 另一条更干净的路是 **Shizuku**：以 adb 权限起独立进程执行 `input`/`uiautomator` 级操作，不开无障碍、不 root。代价是要用户每次开机手动授权一次（或用无线调试自动拉起）。

**设备层：真机 vs 云手机 vs 模拟器**

| 方案 | 成本 | 设备指纹风险 | 结论 |
|---|---|---|---|
| 二手真机农场（一人一机一号） | 300~800 元/台，一次投入 | 最低（官方系统 + 正版 App + 无 root） | **首选**，3~5 台起步 |
| 云手机（ARM 云机） | 30~80 元/台/月 | 中高：GPU/传感器/机型画像异常，部分云端 IP 段已被标记 | 只做**余票监控/低频**，不用于抢单 |
| 本地模拟器（BlueStacks/MuMu） | 零 | 最高（大麦设备可信检测直接针对） | 仅调试脚本，不实战 |

### 3.2 时序设计（成败第一要素）

```
T-30min  预热：App 已登录、进详情页、屏幕常亮、免电省、锁屏关闭、
         无障碍/Shizuku 就绪、NTP 完成 5 次采样取中位数
T-5min   网络：Wi-Fi/4G 择优测 RTT，选低延迟出口
T-10s    定位：回到演出详情页；校验"立即购买/预约抢票"按钮存在
T-200ms  粗等结束 → 1ms 忙等（busy-wait，禁止 sleep）
T-55ms   发射第一击（补偿"点击→服务端收到"的链路延迟）
T+0~60s  连点 / 状态机推进 / 提交重试（间隔 100~300ms，带抖动）
T+成功   停所有其它设备（FIRST_COMPLETED），推送通知，转人工支付
```

**为什么要 T-55ms 而不是 T+0？**
点击 → 触摸事件 → 渲染帧 → 网络栈 → 服务端，整个链路有几十毫秒固定延迟。整点发射等于永远晚一拍。开售瞬间是"先到先得 + 库存按毫秒释放"，55ms 是 ticket-sniper 在淘宝场景验证过的经验值，具体平台要**用压测反向标定**（在非热门演出上打点，测量服务端返回 `sold out` 与时间戳的关系）。

**时钟精度**：NTP 单次采样有 ±30ms 抖动，必须**多服务器 × 多采样取中位数**；有条件的用 GPS 时间或本机 PTP。

### 3.3 状态机（这是系统的核心资产，不是脚本）

把购票流程建模成显式状态机，每个状态定义「识别特征 / 可选动作 / 超时 / 失败重试」：

```
DETAIL(详情) → SESSION(选场次) → SKU(选票档) → QTY(数量) → VIEWER(观演人)
   → SUBMIT(提交订单) → [QUEUE(排队/被挤爆) | ANSWER(答题) | CAPTCHA(滑块)]
   → CONFIRM(订单确认) → PAY(支付，转人工)
```

每态识别特征示例：
| 状态 | 识别 |
|---|---|
| DETAIL | 存在文本「立即购买」/「预约抢票」/「缺货登记」 |
| SKU | 存在 `id=tv_price_name` 或「票档」文本；同级节点含「无票」/「缺货登记」 |
| VIEWER | 存在「观演人」+ 观演人姓名文本 + 右侧 checkbox |
| QUEUE | 文本包含「哎呦喂」「被挤爆」「人数过多」「排队」 |
| CAPTCHA | 存在滑块 WebView 容器 / 「请按住滑块」 |
| CONFIRM | 存在「去支付」 |

**状态机带来的收益**：失败不是"再跑一遍"，而是"知道卡在哪一态、为什么、下次改哪个参数"。

### 3.4 拟人化（猫眼这类行为风控的必需项）

- 点击间隔**非均匀**：基准 120ms + 抖动 ±60ms，禁用 `sleep(0.1)` 固定值；
- 坐标**加随机偏移**：±3~8px（在控件 bounds 内），禁用像素级同一坐标反复命中；
- 动作前加**极短触摸轨迹**：无障碍 click 是无轨迹的，风控能看出来；需要时用 `dispatchGesture` 生成 8~12 个采样点的滑动短路径；
- **单账号单设备单 IP**，不共用；同 IP 出网 ≤ 2 台；
- **轮询限速**：余票监控 ≥ 3~5s 一次（人才会这样看），抢票窗口内才放开；
- 不要在开售前反复刷新详情页（这是最强的机器特征之一）。

### 3.5 延迟预算表（用于定位瓶颈）

| 环节 | 目标 | 手段 |
|---|---|---|
| 时钟偏差 | < 10ms | NTP 多源中位数 + 单调时钟计时 |
| 感知（读状态） | < 30ms | 设备内无障碍节点树，禁 ADB dump |
| 决策 | < 5ms | 预编译动作序列，无 IO |
| 点击下发 | < 20ms | 持久连接（ADB shell 常驻 / 设备内直接调用） |
| 提交重试间隔 | 100~300ms | 带抖动，指数退避上限 800ms |
| **总「进入选座→提交」** | **< 600ms** | 与 AutoX.js 实测 0.5s 同量级；目标压到 300ms |

## 4. 落地路线图

**P0（1~2 周）单机跑通**
- 1 台真机 + 1 个账号；AutoX.js（或 Shizuku + Python）实现状态机；
- 只做「详情 → 选场次 → 选票档 → 观演人 → 提交 → 停在去支付」；
- 在**非热门演出**上跑 20 次，采集每态耗时、失败分布；
- 产出：状态机 DSL + 耗时基线。

**P1（2~3 周）时序与鲁棒**
- NTP 多源校时 + busy-wait 发射 + 55ms 补偿标定；
- 盲点快通道 + 状态机校验的双模切换；
- 排队/答题/滑块三类异常的降级与人工接管通道（手机震动 + 通知 + 悬浮窗提示"立即手动"）；
- 产出：单机成功率从 X% 提到 Y%（用非热门演出做对照实验）。

**P2（2~4 周）多设备编排**
- 3~5 台真机，一台一个账号，独立 4G 出口；
- 调度器：任务下发（演出 ID / 场次 / 票档优先级 / 观演人 / 开售时刻）→ 各机倒计时 → FIRST_COMPLETED 抢占 → 其余急停；
- 观测：每机录屏 + 逐态截图 + 结构化日志，集中落库；
- 产出：成功率看板 + 失败归因分布。

**P3（可选）补一条余票监控旁路**
- 用协议层只做**读**（`detail.getdetail` 轮询，3~5s 一次）+ 回流票监控通知，不碰下单接口；
- 这样避开签名维护成本，同时把"捡回流票"这个高价值场景吃下来。

## 5. 已知坑（踩过的人写下来的）

1. **无障碍驱动不了滑块**：AutoX.js 的无障碍滑动事件常被吞，必须走 `dispatchGesture` 或系统注入触摸事件；OpenCV 只解决"算位置"，不解决"发得出去"。
2. **提交订单会被限流**：「哎哟喂，被挤爆啦」不是失败，是排队——需要的是**持续重试 + 通知转人工**，不是换设备。Get-Ticket 的做法是重试 12~15 次后全屏红色告警 + 震动。
3. **ADB tap 每次 fork 一个新进程就多 25ms**：必须持久 shell（`adb shell` 保持 stdin 打开，逐条写命令）。
4. **大麦是自定义渲染**：控件树在某些页面拿不到，纯控件方案会卡住；坐标 + 节点双模是必要冗余。
5. **华为鸿蒙对无障碍管控严**：后台容易被杀，需要"忽略电池优化 + 屏幕常亮 + 开发者选项不息屏"。
6. **模拟器/root/frida = 设备可信检测的头号靶点**，别在实战机上做逆向调试，逆向用单独一台。
7. **单账号高频跨设备**是最容易的连坐特征：一台设备一个号，别为了"多试几次"在同一账号上切换设备。

## 6. 三条路线横向对比

| 维度 | A 协议 RPC | B 设备内无障碍 | C ADB 主机侧 |
|---|---|---|---|
| 单次下单耗时 | **~13ms/请求** | ~500ms（全流程） | ~200ms（盲点）/ 1s+（dump） |
| 开发成本 | 极高（签名/版本跟踪） | 中 | 中 |
| 维护成本 | 极高（App 一升级就修） | 低（控件文本变了改一行） | 中（分辨率/布局变化） |
| 设备指纹风险 | **高**（改机/模拟器/frida） | **低**（真机裸环境） | 低 |
| 并发能力 | 单机可打几百 QPS | 单机 1~3 单 | 单机 1 单 |
| 被"设备可信检测"针对 | 是 | 否 | 否 |
| 适合 | 黄牛规模化（高风险高收益） | **自用/小团队，首选** | 多平台统一调度 |

**推荐组合：B 为主 + C 做调度与多平台适配 + A 只用来读取（余票监控），不碰下单。**

这样做的本质原因：**下单接口的防线是"设备可信"，不是"请求快"。** 在真机上慢 400ms，比在模拟器上快 500ms 更可能拿到票——因为后者根本进不了下单页。
